# Viewing portal — 0.2 feature batch

## Current delivery

This is a local scaffold, not a launched booking service. Public pages contain only fictional examples. Intake, returning-booking and availability samples share fictional records in browser localStorage; the sample sign-in lasts one hour in sessionStorage. The older owner dashboard examples reset on reload. These are demonstrations, not authentication or a shared database; they do not collect real personal data, send email, call Stripe, or program a lock. No real password or upload fields are enabled. No D1/R2 resources have been provisioned and the migration has not been applied. Existing production routing, site architecture, and deployment configuration are unchanged.

Routes:

- `/viewings`: public visitor intake preview.
- `/viewings/mls`: separate MLS entry; origin is not authentication. The public homepage does not link to this route. Query values are intentionally ignored in this batch.
- `/viewings/status`: sample email-code-gated booking list; choose an individual visit for status and feedback. No real authentication.
- `/owner`: disabled email/password sign-in shell.
- `/owner/demo`: explicitly public, fictional dashboard with approval/cancellation, availability, equal owner permissions, last-owner protection, conversation and activity demonstrations.

- `/owner/availability`: shared sample calendar, unlimited month navigation, day/slot blocks, recurring default ranges, approvals and cancellation notification drafts.

`src/lib/viewings/policy.ts` implements pure eligibility, access-release, overlap, retention and last-owner rules. `contracts.ts` declares future adapters; it does not implement a server. `migrations/0001_viewings.sql` and `0002_booking_flow.sql` establish the durable model and database constraints. The tests exercise policy boundaries and SQLite constraints. Browser demonstrations cannot authorize any real action.

## Agreed product behavior

1. Create a permanent, opaque visitor ID from initial email intake, before a paid identity check. Verify mailbox ownership and authenticate subsequent visits. Email is an account attribute, not the ID or proof of personal identity. Never merge existing records based on an unauthenticated email. Reverify email changes; preserve the visitor ID and audit history.
2. No initial website selfie upload. Non-verified-agent visitors use Stripe's hosted government-ID and matching-selfie checks. Require both checks; trust signed provider events or authenticated server retrieval, not browser redirects. Record verified, needs-retry, pending or canceled outcomes. Reuse a pending Stripe session on retries; do not automatically create another paid session for repeated button clicks.
3. Ask explicitly whether the requester is a licensed real-estate agent. Collect licensed name, license number, issuing state and brokerage once, editable later. The initial verified email is the business email; do not ask for a second email. Verify active licensure plus ownership of an independently sourced business contact. A public license number or an MLS URL alone is insufficient. Store source, time, reviewer and a bounded review validity period. Recheck changed or stale credentials. Public lookup automation/API availability remains unconfirmed.
4. Verified agents can skip Stripe and have no required selfie. They may request a private showing and must attend, including when bringing clients. Buyers and unresolved agents receive only owner-coordinated viewing options; they do not receive automatic keybox codes. Owners decide attendance arrangements. Stripe success never independently grants private access.
5. Public and MLS routes share accounts and bookings. MLS query fields, if later supported, are untrusted, bounded prefills, never approval flags. Prefer opaque referral IDs; do not expose sensitive data in URLs. Verify signed referrals when supported and store that separately from source. Returning users retain verification across routes.
6. Every booking is requested before approval. Dots may process routine requests under owner-configured rules; ambiguous cases go to an owner. Owner settings must define hours, duration, buffers, lead time and automatic approval conditions. No automatic approvals are configured in this batch.
7. Calendar display uses America/New_York with daylight saving handling; persistence uses UTC. Server recomputes eligibility and reserves slots atomically. Requested and approved reservations block overlap. Pending request expiry/hold duration must be configured. Rescheduling increments revision, reserves the new time atomically, invalidates old jobs and revokes old access; history remains.
8. Dedicated sender: `rockybottom128@gmail.com`, via authorized Gmail API access. After approval, provision the timed PIN and email access instructions as soon as installation is confirmed, before the visit begins. This supersedes the earlier 60-minute-before delivery proposal. PIN activation is separate from email delivery and limited to the approved access window. Verify installed PIN and current booking revision, agent status, attendance and automation state at send time. No code before approval/installation, after start, or for owner-coordinated visits. Store a protected code reference against the booking and revision, not a reusable visitor-wide code. Late approvals need an explicit owner-handled path.
9. igloohome Lockbox SK4/SK4X is the target. Use direct API integration; Home Assistant is not required. A Bridge is recommended for confirmed remote revocation, custom codes and current status. Confirm model/firmware, subscription, time precision, daylight saving and revocation semantics on actual hardware. Do not confuse an API job accepted response with a confirmed installed code. Offline algoPIN support does not imply immediate remote cancellation.
10. Save questions, feedback, replies, approval history, verification attempts and delivery outcomes. Authenticated visitors may access only their own records. Give owners a shared dashboard with equal permissions and a pause switch. Deleting an owner removes access and immediately revokes sessions; historical actor references remain. All owners may invite/remove owners; protect the last active owner transactionally.

## Email, availability and returning visits

The current sample uses an eight-digit random email code. Visitor password support remains an open product decision; email-code-only sign-in was an implementation recommendation, not a confirmed owner preference. The email label asks agents to use their business email. On first send, normalize and upsert the draft visitor; existing visitors retain the same ID. Send the same neutral response for both. Verify server-side before showing the agent question or any existing account data. Reuse valid verification on later requests; changing agent details triggers review. Persist only a keyed digest of the code, a generation, expiry, attempts and consumption. Resend replaces the previous challenge. Use a 10-minute expiry, five attempts, send cooldown and server-side email/IP rate limits. Successful verification atomically consumes the challenge and creates a secure HttpOnly session. Owner accounts still use passwords through the selected auth provider.

The visitor calendar begins with the current Sunday–Saturday week: four rows Sunday–Wednesday; five rows Thursday–Saturday. Past dates/times are disabled. Selecting a day displays time tiles underneath. Sample slots are hourly 9 AM–5 PM Eastern; actual hours, buffers and lead time are still owner configuration. Server reservation must enforce this rolling horizon as well as availability. Owners can navigate any month and block/unblock whole days or individual slots. Multiple weekly/default blocked ranges are supported. Whole-day blocks win; explicit slot exceptions override recurring ranges. Unblocking a day restores its underlying slot/default rules, not necessarily all slots. Unblocking never restores canceled reservations.

A block that overlaps requested or approved bookings requires a cancellation reason and explicit agreement to notify affected visitors. Present the affected bookings before confirmation. Live implementation must atomically save the block, cancel reservations, increment revisions, invalidate queued access/email jobs and queue notice drafts containing the reason. Revoke already installed PINs and expose failures. Owner approval, PIN setup and notification delivery have distinct statuses; a submitted request is not a confirmed visit. Approval of a private showing starts code setup; confirmed installation allows the access email immediately, while the code itself remains time-limited. Buyer confirmations contain time and owner instructions only.

Confirmation email and the permanent **My bookings** navigation link lead to `/viewings/status`. An expired/missing session redirects the visitor through email-code sign-in. The preview shows a sign-in prompt instead and demonstrates it using a visible fictional inbox. A returning visitor can hold multiple bookings, select one by day/time, and see its status. Questions/feedback become available at that booking’s start time for approved/completed visits only, with the same rule enforced on the server. Messages are attached to a booking ID. Future bookings offer cancellation and a link to request another time; transactional rescheduling remains a server integration task.

## Visitor password design proposal (awaiting preference)

Offer optional password creation after first email verification, while retaining email-code sign-in for visitors who prefer it. Returning agents reuse their existing profile and valid credential verification regardless of sign-in method. A password never waives agent verification or independently authorizes access. Owners retain required password accounts.

Design account settings with Set password / Change password, Forgotten password, and sign-out controls. Require a recent verified session to set/change a password, and a single-use expiring email recovery challenge to reset it. Store salted one-way password hashes through the selected maintained authentication implementation, never reversible encrypted passwords. Reset/recovery must revoke existing sessions and be rate-limited. Do not collect any real passwords in the static preview. Wire this design into the server authentication phase before live accounts, after the owner chooses optional passwords, required passwords, or email codes only.

## Selfie privacy and retention

Government-ID images are collected by Stripe, never copied into website storage. Persist only necessary results and references, not entire provider payloads, ID numbers or addresses. If permitted, retrieve only the successful Stripe selfie using restricted credentials soon after verification and store in a private R2 bucket. Never put photos, signed URLs, tokens or access codes in logs, emails, analytics, audit descriptions or repository files. Owner image requests require server authentication and authorization, short-lived access and no-store responses.

The user approved 90-day selfie retention. Proposed implementation: set an initial expiry 90 days after successful capture; after completed viewings, use 90 days after the last completion. The earlier proposed listing-closure cleanup and treatment of future bookings still need a final policy. Do not retain forever for incomplete bookings. Cleanup must remove the R2 object and its reference; deleting a Stripe session does not delete our copy. Document separate backup-retention behavior. Retention jobs are not active yet.

Intake must explain Stripe's own handling separately from our promise not to copy ID images, the retained selfie, purpose, owner access, retention and deletion contact. Obtain explicit consent before collection. Stripe's terms restrict housing-eligibility use and discuss alternative verification; confirm that the self-guided viewing use and retained-selfie purpose are permitted before enabling live intake. Do not silently present a failed automated check as a housing decision.

## Server implementation remaining

- Choose a maintained email/password authentication library/provider compatible with Astro Workers; benchmark secure password hashing against free CPU limits. Never weaken hashing to fit a plan. Add sessions, CSRF/origin protection, reset/invite tokens, rate limits and optional MFA. No public owner self-registration. Visitor email verification and owner invitation must not leak account existence.
- Add D1 binding in a separately configured development environment; apply/test migrations locally before remote use. Add private R2 only after consent and retention policy are finalized. The schema currently has no production auth tables; selected auth library migrations own hashes and sessions.
- Implement authorized server handlers for draft registration, session verification, agent review, availability, reservation/reschedule/cancellation, messages, owner management and selfie viewing. Never accept client verification booleans or actor IDs as authoritative. SQL constraints supplement, not replace, authorization and validation. Limit text lengths and render messages as text.
- Implement Stripe create/retrieve/webhooks with raw-body signature verification, replay/event deduplication, account binding, document+selfie requirements and restricted selfie retrieval. A provisional session-link/API permission review is required; do not put Stripe redirect URLs into persistent logs or email.
- Implement igloohome and Gmail adapters and a durable scheduler/outbox. Claim jobs atomically with leases, revalidate before external actions and serialize cancellation/send races. Deduplicate per booking revision. An uncertain Gmail send must be reconciled by provider message state or flagged to owners, not blindly retried with a second code email. Failed revocations must be visible and keep new private access blocked until resolved.
- Provide Dots with a narrowly scoped service identity and tools over the same server rules: list pending work, record sourced verification evidence, approve under configured policy, request access provisioning, draft/send allowed replies, and escalate. Do not let untrusted visitor messages modify policy or invoke arbitrary unlock. Owner management is reserved to authenticated owners. No agent automation or skill is installed in this batch.
- Provision secrets through the hosting secret store, never browser bundles or source. Keep development and production databases, email recipients, Stripe mode and lock credentials separate. Preview builds must not send real mail or operate a real lock. A feature flag alone is insufficient without separate credentials and server authorization.
